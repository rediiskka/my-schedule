# Моё расписание — инструкция для работы над проектом

Это правила, по которым здесь пишется код. Они обязательны, а не желательны.
Взяты из raspisanie-3bi1, на котором этот сайт и построен, — расхождений между
двумя проектами быть не должно.

## Идеал

**Профессиональная разработка, но прагматичная.** Держим оба конца:
дисциплина инженера и здравый смысл человека, который помнит масштаб задачи.

Профессионально — значит: понятные имена, одна ответственность на функцию, никакого
дублирования знания, цвета в токенах, разделы в файле, комментарий объясняет «почему»,
за собой убрано, перед сдачей проверено глазами.

Прагматично — значит: без сборщиков, фреймворков и слоёв абстракции там, где хватает
десяти строк. Масштаб решения соответствует масштабу задачи.

**Быдлокод запрещён.** Быдлокод — это не «некрасиво», это конкретные вещи:

- копипаста вместо общей функции;
- захардкоженные цвета, размеры и строки вместо токенов и констант;
- функция-полотно, которая делает всё сразу;
- имена `tmp`, `data2`, `func1`, `flag`;
- `!important` и `z-index: 9999` вместо разбора, почему правило не применилось;
- закомментированный код «на всякий случай»;
- правка, после которой никто не смотрел на результат;
- «потом поправлю».

Ни один из пунктов не оправдывается тем, что «проект маленький». Маленький проект —
это повод писать аккуратно, а не небрежно: здесь просто нет объёма, за которым можно
спрятать грязь.

Три вещи, которые нарушать нельзя:

1. **Не усложняй.** Простое рабочее решение лучше умного. Новая сущность появляется
   только тогда, когда без неё задача не решается.
2. **Не оставляй мусор.** Всё, что перестало использоваться, удаляется в той же правке.
3. **Не говори «готово», не посмотрев глазами.** Смоки обязательны — см. конец файла.

## Что здесь лежит

```
index.html      весь сайт: разметка, стили, логика — один файл
my-data.json    личные записи, зашифрованные пофрагментно
index.json      зашифрованный индекс к ним: даты и позиции
*.local.json    тестовые записи для проверки вёрстки, вне git и только на localhost
docs/
  how-it-works.md   формат файлов, вывод ключа, что видно постороннему
tools/
  vault.py      правка личных записей: list / add / edit / rm
```

Сайт лежит в корне репозитория: так GitHub Pages отдаёт его по адресу без подпапки.

Запуск: `python -m http.server 8742` из корня, открывать `http://localhost:8742`.
Правка записей: `python tools/vault.py list` (пароль из `.env`, он в `.gitignore`).

## Архитектура

**Расписание группы приходит извне.** Сайт тянет `data.json` из raspisanie-3bi1 —
там оно и обновляется. Копии здесь нет намеренно: её пришлось бы помнить обновлять,
а забыв, сайт молча показывал бы прошлый семестр как настоящий. Источник недоступен —
честная заглушка. Своей сборки данных здесь нет: парсер живёт в том проекте.

**Сайт только читает, пишет утилита.** Pages отдаёт статику, писать в репозиторий
из браузера нельзя — значит запись, заведённая в интерфейсе, осталась бы в одном
браузере. Поэтому формы задачи на сайте нет вовсе, а `tools/vault.py` правит файлы
с машины, и результат уезжает обычным коммитом.

**Личное шифруется, публичное — нет.** Расписание группы публичное, прятать нечего.
Личные записи лежат отдельными зашифрованными фрагментами, индекс к ним тоже
зашифрован. Подробности — `docs/how-it-works.md`, там же граница того, что схема
обещает, а что нет.

**Парсер тупой, сайт умный** (правило исходного проекта, действует и здесь). Данные
описывают, что есть; решения о показе принимает `index.html`.

Поля занятия: `subject`, `type`, `teacher`, `room`, `subgroup`, `spectime`,
`dateOverride`, `note`, `raw`.

**Поля для правок — часть структуры, а не отдельный файл.** Нужно перенести пару или
предупредить людей — дописываешь `dateOverride` или `note` прямо в `data.json`.
Сайт разберётся, как это показать.

**Решения принимает сайт.** Куда поставить занятие, какое время показать, что вынести
в заметку — всё это логика отображения и живёт в `index.html`.

**Сайт не врёт и не пересказывает таблицу.** Он показывает итоговое расписание. Если по
субботам пары идут по своему времени — он показывает это время, а не сноску «смотри
внутри ячейки». Если в источнике противоречие, которое нельзя разрешить, — он не решает
за деканат, а честно пишет об этом заметкой у пары.

## Как писать код

**Бритва Оккама.** Не добавляй сущность, пока без неё не получается. Отдельный файл
правок, слой абстракции, «на будущее» — всё это надо заслужить реальной задачей.

**KISS важнее всего.** Сайт читают студенты, а поддерживает один человек. Если решение
требует схемы на салфетке — оно неверное. Из двух рабочих вариантов берётся тот, который
проще объяснить.

**Не оверинжинирь.** Это сайт с расписанием одной группы: одна страница, три вида,
пара фильтров. Профессионально здесь — не «применить весь арсенал», а решить задачу
минимальными средствами. Чего в этом проекте делать не нужно:

- сборщик, транспайлер, фреймворк, менеджер пакетов;
- разбиение на модули и слои ради самого разбиения;
- абстракции под гипотетические будущие требования;
- собственный роутер, стор состояния, система событий;
- кэш, воркеры, оптимизация того, что и так мгновенно;
- покрытие тестами того, что проверяется взглядом за пять секунд.

Признак оверинжиниринга: кода на инфраструктуру больше, чем на саму задачу.
Если решение нельзя объяснить в двух предложениях — оно слишком сложное для этого сайта.

Правило разрешения спора: сначала самое простое, что работает. Усложняй только когда
простое сломалось на реальном случае, и в комментарии напиши, на каком именно.

**Держись середины.** Обе крайности одинаково плохи, и свалиться легко в любую:

| Недобор | Норма | Перебор |
|---|---|---|
| копипаста в трёх местах | общая функция | фабрика функций и слой абстракции |
| магические числа по всему файлу | токен в палитре | генератор токенов и тема как плагин |
| функция на 80 строк | 3–4 маленькие плюс оркестратор | 15 функций по две строки |
| «и так понятно» | комментарий про «почему» | комментарий к каждой строке |
| правка на глаз без проверки | смок по четырём ширинам | автотесты на вёрстку |
| один файл-свалка | один файл с разделами | десять файлов и сборщик |

Правая колонка для этого проекта такая же ошибка, как левая. Если рука тянется сделать
«как на большом проекте» — остановись и спроси, что это даёт здесь и сейчас.

**Одна вещь делает одно.** Функция считает или рисует, но не оба сразу. Класс отвечает
за один компонент. Если в имени появляется «и» — пора делить.

**Не дублируй знание.** Цвет живёт в токене, а не в пяти правилах. Список полей
состояния — в одном месте, а не в чтении и записи по отдельности. Одинаковая разметка
собирается общей функцией.

**Функция делает одно (SRP).** Не пиши полотно на пятьдесят строк, которое и данные
считает, и разметку собирает, и в DOM кладёт. Раздели на маленькие функции с понятными
именами, а сверху поставь оркестратор, который их вызывает по порядку. Оркестратор
читается как оглавление:

```js
// плохо: одна функция знает всё
function renderEverything(){ /* 60 строк вперемешку */ }

// хорошо: маленькие делают, оркестратор соединяет
function render(){
  const marks = nowMarks();       // что сейчас идёт
  renderContent(marks);           // список / неделя / месяц
  fillPicker();                   // селектор в шапке
  renderDay();                    // попап дня
  syncUI();                       // активные кнопки и поля
}
```

Признак, что пора делить: в функции появился комментарий вида «а теперь соберём…».
Этот комментарий — имя будущей функции.

**Имена честные и единообразные.** Имя говорит, что вернётся или что произойдёт:
`lessonTime()` возвращает время, `renderDay()` рисует, `applyShift()` применяет.
Не сокращай до неузнаваемости: `sgTint` понятно рядом с подгруппами, `sgT` — уже нет.
Одна сущность — одно слово во всём проекте: если занятие `lesson`, то везде `lesson`,
а не `lesson`, `item` и `l` вперемешку.

**Комментарий объясняет «почему», а не «что».** Что делает строка, видно из кода.
Ценно другое: почему сделано именно так, какой баг это лечит, что сломается при откате.

```js
// плохо
// перебираем пары
p.lessons.forEach(...)

// хорошо
// Порядок — по времени, при равном — по аудитории: так ни одна подгруппа
// не оказывается «главной», а цвет закреплён за подгруппой, а не за стороной.
p.lessons.sort(...)
```

У каждой неочевидной функции — строка сверху о том, зачем она нужна. Тривиальные
однострочники комментария не требуют.

**Не мусорь.** Убрал возможность — убери и её стили, и её классы из разметки.
Мёртвые правила накапливаются незаметно и потом стоят часов разбора. Проверять так:

```bash
grep -c "\.имякласса[{ ,:]" index.html   # объявлено
grep -c "имякласса" index.html            # используется
```

**Секции обязательны.** И стили, и скрипт разложены по разделам с одинаковыми
заголовками. Новое правило кладём в свой раздел, а не в конец файла.

## Не изобретать велосипеды

Почти всё, что хочется написать руками, браузер уже умеет. Прежде чем писать логику —
проверь, нет ли готового механизма. Родной почти всегда короче, быстрее и надёжнее
самописного.

| Задача | Готовое решение | Чем плох велосипед |
|---|---|---|
| Прилипающая панель | `position: sticky` | пересчёт на скролле отстаёт на кадр, панель дрожит |
| Реакция на размер окна | `ResizeObserver` | событие `resize` не ловит плавное перетаскивание |
| Раскрывающийся блок | `<details>` / `<summary>` | свой тумблер — это состояние, обработчик и доступность руками |
| Рамка, не меняющая размер | `outline` + `outline-offset` | `border` двигает содержимое на свою толщину |
| Смешать цвет с фоном | `color-mix()` | второй захардкоженный цвет, который забудут поменять в тёмной теме |
| Ширины колонок | `grid-template-columns`, `fr`, `minmax` | арифметика в процентах ломается на первом же изменении |
| Хранение состояния | адрес страницы (`#hash`) | своё хранилище не расшаришь ссылкой и не переживёшь обновление |
| Позиция без сдвига раскладки | `transform: translate` | смена `left`/`margin` вызывает пересчёт всей страницы |

Современные возможности, на которые здесь опираемся и которые можно смело использовать:
CSS-переменные, `color-mix`, `clamp`, `min`/`max`, логические свойства, `:focus-visible`,
`prefers-color-scheme`, `prefers-reduced-motion`, `fetch`, `async/await`, опциональная
цепочка `?.`, `??`, `Intl` для дат и чисел.

## Практики вёрстки и стилей

**Семантика вперёд.** `<button>` для действия, `<details>` для раскрытия, `<table>` для
таблицы недели. Дивы с обработчиками — только когда семантического тега правда нет.
Семантика даёт клавиатуру, скринридер и правильное поведение бесплатно.

**Доступность — это не отдельная задача.** У иконки-кнопки есть `aria-label`, у
декоративной картинки `aria-hidden`, у полей — `<label for>`. Фокус виден. Проверка:
пройди страницу с `Tab`, ничего не должно потеряться.

**Единицы по смыслу.** `rem`/`em` для типографики и отступов внутри компонента, `px` для
границ и мелких деталей, `%`/`fr`/`vw` для раскладки. Не мешать без причины.

**Раскладка — flex и grid, а не отступы.** Расстояние между элементами задаёт `gap`
родителя, а не `margin` каждого ребёнка: не будет схлопывания и лишних правил
«у последнего убрать».

**Селекторы плоские.** Один класс — один компонент. Вложенность не глубже двух уровней,
`!important` — признак того, что где-то нарушен порядок правил. За `#id` в стилях
цепляемся только для уникальных узлов раскладки.

**Имена по смыслу, не по виду.** `.note`, а не `.blue-box`. Через месяц цвет поменяется,
а имя останется.

**Прогрессивное улучшение.** Данные не загрузились — сайт показывает заглушку, а не
белый экран. Скрипт упал — каркас на месте.

**Анимируем только `transform` и `opacity`.** Остальное заставляет браузер
пересчитывать раскладку на каждом кадре. И уважаем `prefers-reduced-motion`.

## Стили

**Ни одного цвета вне палитры.** Все цвета — в `:root` и `html[data-theme="dracula"]`.
Схема токенов:

| Токен | Что это |
|---|---|
| `--blue`, `--mint`, … | акцент, фон плашки |
| `--blue-ink` | насыщенный вариант: контуры иконок, мелкий текст |
| `--blue-soft` | мягкая заливка внутри иконок |
| `--on-accent` | текст поверх любой акцентной плашки |
| `--sg0/1/2` | подгруппы: общая пара, первая, вторая |

Тёмная тема переопределяет их **все**, а не только фон. Проверка простая: если добавил
цвет и не дописал строку в тёмную тему — ты сломал тёмную тему.

**Порядок правил решает.** Переопределение, стоящее выше базового правила, не работает.
Медиа-запрос кладём после блока, который он правит. Ошибка тихая: правило выглядит
написанным, но не применяется.

**Шорткат `padding` у элемента, который сам является `.wrap`, убивает его горизонтальные
отступы.** Пиши `padding-top` / `padding-bottom`.

**Геометрия одинаковая у всех состояний.** Рамка «сейчас» рисуется через `outline`, а не
`border`: иначе строка съезжает на толщину рамки, и колонки перестают быть соосными.
Цветная полоска слева — накладкой `::before`, а не `border-left`, по той же причине.

## Раскладка

Модель панели: **панель лежит слоем ниже содержимого и выходит из-под его края.**
Она никогда не накрывает контент.

- Свободного поля хватает на панель целиком → панель стоит рядом, кнопки нет,
  ничего не двигается.
- Не хватает → панель и лист разъезжаются навстречу: панель проходит `поле`,
  лист уступает `ширина панели − поле`. В сумме всегда ширина панели.

Липкость — только нативный `position: sticky`. **Никаких пересчётов на скролле:**
позиция, посчитанная в JS, отстаёт на кадр, и панель дрожит на микропиксели.

Раскладка считается инлайн-скриптом сразу после `<body>` — до первой отрисовки.
Иначе первый кадр рисуется по-старому и всё прыгает.

## Плавность

Мигание и дёрганье — это баг, а не мелочь. Известные источники:

- Внешние CSS/JS по CDN дособирают стили после загрузки. Внешних библиотек в проекте
  нет и быть не должно — всё своё.
- Анимация появления на каждом рендере. Рендер идёт и по таймеру — значит мигает само.
- Блок, меняющий высоту после загрузки данных (виджет погоды). Размер задаётся заранее.
- Тема, выбранная после первой отрисовки. Выбирается в раннем скрипте.

## Красота

**Соосность.** Время, названия и плашки аудиторий стоят на одной вертикали во всех
строках. Глаз не должен бегать.

**Единая разметка карточки.** Одиночная пара и сдвоенная выглядят одинаково устроенными.
Сдвоенная — одна карточка с пунктиром посередине, а не две отдельные плашки.

**Цвет несёт смысл.** Заливка говорит о подгруппе, а не украшает. Если цвет ничего не
значит — он лишний.

**Иконки свои, контурные, из общего спрайта.** Системные эмодзи выглядят чужеродно
и на Windows часто рисуются монохромными.

## Смоки — обязательно

Не говори «готово», пока не посмотрел глазами. Минимальный прогон после любой правки
вёрстки:

| Ширина | Что проверить |
|---|---|
| 390 | телефон: меню, попап дня целиком без прокрутки, месяц по высоте |
| 768 | планшет: сетка недели, инфо-блок |
| 1200 | панель толкает контент, соосность строк |
| 1700 | панель стоит рядом, контент по центру |

Плюс каждый раз: список / неделя / месяц, светлая и тёмная тема, открытие и закрытие
меню, смена его стороны.

Синтаксис скрипта проверяется отдельно — он живёт внутри HTML и опечатка не видна:

```bash
python -c "import io,re; open('/tmp/a.js','w',encoding='utf-8').write(re.findall(r'<script>([\s\S]*?)</script>', io.open('index.html',encoding='utf-8').read())[-1])"
node --check /tmp/a.js
```

## Что не делать

- Не возвращать внешние библиотеки ради пары контролов.
- Не двигать элементы скриптом там, где справляется CSS.
- Не хардкодить цвета, размеры панели и ширину контента — они в токенах.
- Не оставлять правило «на всякий случай». Не используется — удаляй.
