# Как это устроено

Сайт с расписанием лежит на GitHub Pages. Пары приходят из репозитория группы
`raspisanie-3bi1` — это публичное расписание, копии здесь нет. Личные задачи и цели лежат рядом, в том же
репозитории, но зашифрованными.

Репозиторий публичный, и это осознанно: скрывать нечего, кроме содержимого
личных пунктов, а его прячет шифрование, а не закрытость репозитория.

## Кто что делает

```
tools/vault.py  ──пишет──>  my-data.json + index.json  ──читает──>  index.html
   (с машины)                  (в репозитории)                        (в браузере)
```

**Сайт только читает.** Pages отдаёт статику: писать в репозиторий из браузера
нельзя. Поэтому в интерфейсе нет ни формы задачи, ни кнопки «добавить» — пункт,
заведённый в браузере, остался бы в этом браузере и на другом устройстве не
появился бы. Ровно та беда, ради которой всё и переехало в файл.

**Файлы правит утилита** `tools/vault.py`, запускаемая с машины. Результат
уезжает обычным коммитом, Pages пересобирается за минуту, и на всех устройствах
сразу свежее расписание.

## Формат файла

Один и тот же для задач и целей:

```json
{
  "v": 2,
  "kind": "tasks",
  "salt": "<base64, 16 байт>",
  "items": ["<base64>", "<base64>", ...]
}
```

Каждый элемент `items` — **отдельный пункт со своим вектором инициализации**.
Отсюда два свойства, ради которых так и сделано:

- новый пункт дописывается **одной строкой**, прежние остаются байт в байт теми
  же — файл читается в diff'е и не переписывается целиком;
- пункт правится точечно, не задевая соседние.

Фрагмент внутри:

```
base64( iv[12] ‖ AES-GCM(key, блок)[512+16] )

блок = size[2] ‖ json ‖ нули до 512 байт
```

Два байта настоящей длины впереди, дальше json пункта, дальше набивка нулями.
`size == 0` — пустышка, при чтении она даёт `null` и пропускается.

Поля пункта расписания: `id`, `title`, `date` (ISO), `time`, `duration`,
`category` (`study`/`work`/`personal`/`other`), `note`, `done`.
Поля цели: `id`, `title`, `horizon` (`month`/`season`), `period`, `note`, `done`.

## Ключ

Из пароля выводится PBKDF2-HMAC-SHA256, 150000 итераций, соль — 16 байт из
файла. Результат — 32-байтный ключ AES-GCM.

**Соль лежит в самом файле, а не в браузере.** Иначе на втором устройстве из
того же пароля вывелся бы другой ключ и файл не открылся бы. Поэтому порядок
такой: пароль → скачали файл → взяли соль → вывели ключ → расшифровали
фрагменты.

Пароль на сайте служит двум вещам сразу: пускает внутрь (в `index.html` лежит
его SHA-256) и даёт ключ к файлам. Ключ живёт в `sessionStorage` до закрытия
вкладки — сам пароль после входа нигде не остаётся.

## Что видно постороннему, а что нет

Открыто и так задумано: алгоритм, число итераций, соль, хэш пароля. Стойкость
держится только на пароле — прятать параметры схемы бессмысленно, сайт обязан
их знать, а его код видит каждый, кто открыл страницу.

Скрыто содержимое пунктов: названия, даты, время, заметки. Указателя по датам
намеренно нет — быстрый ответ «занято ли 14:00 десятого» без ключа и был бы
расписанием наружу. Расшифровать весь файл дешевле, чем кажется: сотня пунктов
— около 2 мс, две тысячи — 14 мс.

Форму файла тоже пришлось закрыть, иначе она выдавала бы то, что шифротекст уже
спрятал:

- **все фрагменты одной длины** — иначе по размеру видно, насколько подробный
  пункт;
- **число фрагментов кратно 16, остаток добит пустышками** — иначе видно,
  сколько всего дел и когда их стало больше.

Чего схема не обещает: файл может скачать кто угодно и подбирать пароль у себя
сколько угодно. Стойкость упирается в пароль и в 150000 итераций, не больше.

Потеря пароля — потеря задач. Восстановления нет и быть не может: расшифровать
файл без пароля нельзя по построению.

## Работа с файлами

Пароль берётся, в порядке приоритета: `--password`, переменная окружения
`SCHEDULE_PASSWORD`, файл `.env` рядом с репозиторием (он в `.gitignore` и
никогда не коммитится), запрос в консоли.

```bash
# посмотреть, что внутри
python tools/vault.py list tasks.json
python tools/vault.py list tasks.json --date 2026-09-10

# завести пункт
python tools/vault.py add tasks.json --title "Сдать курсовую" \
    --date 2026-09-10 --time 14:00 --duration 90 --cat study --note "глава 2"

# поправить и удалить (id — первые 8 символов из list)
python tools/vault.py edit tasks.json --id 5019e955 --time 16:00
python tools/vault.py rm tasks.json --id 5019e955

# залить пачку из обычного json
python tools/vault.py import tasks.json draft.json

# цели живут отдельно, команды те же
python tools/vault.py add goals.json --title "Закрыть сессию без троек" \
    --horizon season --period "осень 2026"
```

После правки — обычный коммит и push. Дальше минута-две, пока GitHub пересобирает
Pages, и задача появляется на всех устройствах.

Файл запрашивается мимо всех кэшей сразу: `cache: 'reload'` снимает кэш браузера,
а метка `?v=<время>` в адресе — кэш самого GitHub Pages. Без второго голый
`tasks.json` лежит у них готовым ответом, и сайт ещё несколько минут показывал бы
вчерашние задачи, хотя файл уже обновлён.

Сама страница `index.html` кэшируется браузером как обычно. Если после коммита
интерфейс выглядит старым — Ctrl+F5.

## Цели и расписание

Цели (`goals.json`) — это то, у чего нет часа и дня: «закрыть сессию без троек»,
«дочитать три книги за сентябрь». Они живут дольше пунктов расписания и потом
раскладываются на конкретные задачи с датами, которые уезжают уже в `tasks.json`.

Держать их в одном файле с расписанием — значит потом выкапывать их оттуда среди
сотен дел, поэтому файлы разные, а формат и утилита общие.

## Локальный запуск

```bash
python -m http.server 8742
```

и открыть `http://localhost:8742`. Файлы `tasks.json` и `goals.json` берутся
из корня репозитория, так же как на Pages.
